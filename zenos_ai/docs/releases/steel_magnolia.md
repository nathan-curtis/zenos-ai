# Release Notes — 2026.9.0 'Steel Magnolia'

**Status:** Beta — ETA Saturday, 2026-09-05
**Branch:** `feat/2026.9.0`
**Base:** 2026.8.0 'Chef'

---

## Summary

Hospitality starts with knowing what's actually going on: who's in the room, whether they're staying the night, what they're allergic to, whether a door just opened for a person or a raccoon. Steel Magnolia is the release where the house learns to tell the difference, then gets out of the way — the room is just warm, the allergy is already flagged, and none of the effort behind it is visible day to day.

Room Manager v3 is the clearest example: a full rewrite of how a room decides what state it's in, replacing a legacy `checking_timer` hack with a real wasp-in-a-box model, adding `entertaining_hold`/`guest_hold` as opt-in signals instead of a blanket toggle, and gating asleep-detection to nighttime so a hamper on a bed doesn't put a room to sleep at 2pm. It started as an incident — an early redesign attempt broke the legacy Node-RED controller live — and the rebuild is isolated by design so that can't happen again.

Twenty CRM's structured stay/appointment/service-request objects and Room Manager's shared occupant-prefs lookup are the other half of the same idea: Kitchen's allergen flagging and guest-aware meal planning both read from one source of truth about who's staying where, instead of five systems each guessing separately. That same lookup now runs both directions in time — the household gets a heads-up ahead of an arrival with the guest's prefs in hand, and a nudge as a checkout approaches, not just a record after the fact.

The rest of the release is plumbing that makes the front-of-house stuff trustworthy — ZQ-1 now flags a silently-empty query instead of returning a false zero, recorder stats stopped lying about energy sensors, Friday's prompt gets real room-state data for the first time, and the architecture docs were checked chapter-by-chapter against actual code.

And a good host knows which doors don't open themselves: locks, exterior covers, and the alarm panel all gain a real identity gate this release — not just "can the agent call this tool" but "has the household said yes to this specific risky thing, right now." Building it surfaced a real self-escalation hole in how certifications were granted, closed the same day it was found, plus a second gap discovered later in how those certs get audited — closed the same way.

## Room Manager v3 — The Living Room-State Engine

Taskmaster got the glow-up in Chef — a new file, a new expediter identity, top billing in the release notes. Room Manager sat in the next chair the whole time, running the same `checking_timer` hack it shipped with, and it noticed. This release is Room Manager's turn in Truvy's chair: same bones, same name, walks out looking like it's never had a bad hair day in its life. See [Room Manager v3 & REFLEX](../architecture/22_Room_Manager_v3_REFLEX.md) for the design doc and [the operator's manual](../getting_started/room_manager_operators_manual.md) for the plain-language version.

**It started as an incident, not a makeover.** An early pass at converting real rooms to a new control select deleted and replaced `input_select.<room>_control` — still the household's actual production controller, owned by legacy Node-RED, running in parallel with v3 the entire time. That broke Node-RED live, mid-house. Full revert first, then the redesign below, built specifically so it can't happen that way again.

- **`room_control_manager` — the actual fix.** A new control surface, `select.<room>_control_manager`, with zero shared entity, label, or code path with legacy `input_select.<room>_control`. The domain-agnostic fallback chain that caused the original break (checking `input_text` before `input_select`) is gone entirely, not patched. Persistence moved off a per-room `input_text` helper onto a single cabinet-backed dict drawer, keyed by room — the select itself does nothing on `select_option` but fire an event; the dispatch script's listener is the sole writer. Named by ownership (`_control_manager`), not version (`_v3`), specifically so the *next* revision doesn't force another live-entity migration.
  - Caught a real orphaned-registry bug along the way: reusing the same `unique_id` across two revisions of the select (input_text-backed, then cabinet-backed) silently blocked re-registration entirely. If you ever see a template select sit at `unknown` with null `friendly_name`/attributes through multiple reloads, that symptom is this bug, not a template error — fixed here with a distinct `_cab` suffix.

- **Wasp-hold, actually wasp-in-a-box now.** The old mechanism armed a 2-minute `checking_timer` on a door open and showed `checking` while it ran — `checking` no longer exists as a producible state anywhere in the system. First replacement (superseded later this same release, see "Wasp/hold rewritten again" below): a `wasp_door` opening floored the room to `occupied` immediately and cleared a latched wasp flag; motion firing while every `wasp_door` for the room was closed set that flag and the cascade showed `hold` instead of confidently resolving to `occupied`. The flag was a self-referencing template attribute, not another `input_boolean` — deliberately, to avoid a new per-room helper entity.
  - `mode=label_discover`'s `group_warnings` now catches a lock+door pair tagged for the same opening and flags it — tag the door (`wasp_door`), never the lock. Caught live on a real shared entry where the lock was correctly tagged and the door itself was never in `trigger_entities` at all.

- **`entertaining_hold` / `guest_hold` — two more `hold` sources, opt-in by label, not a blanket toggle.** Legacy Node-RED held occupancy conservatively per-room the whole time `input_boolean.entertaining` was on — confirmed live that an HA reload's connectivity blip put five legacy rooms into Hold simultaneously, all at once, for no room-specific reason. The v3 equivalent scopes that same signal down to exactly the rooms that opted in: tag the *existing* `input_boolean.zen_entertaining` (or `zen_guest_mode`) with a purpose label plus the target room's own label. Nothing new created. Both outrank `occupied`/`vacant`, both outranked by `engaged`/`asleep`/manual override/emergency.

- **Asleep window — night gates the signal, doesn't replace it.** A direct `asleep`/`bed_occupancy` signal firing during the day — the real case that found this: a laundry hamper set on a bed tripped the bed sensor — previously auto-slept the room in broad daylight. Fixed with a default-on gate against the household's real scheduler-anchor clock (`zen_night_start`/`zen_am_start`), deliberately *not* `sensor.period_of_day`, a different sun-elevation-based sensor with no relation to those anchors that looks like a natural fit and isn't. Gated identically at three separate enforcement points — the live-gate, the edge-triggered timer-arming handler, and the periodic room-timer reconcile pass — because the reconcile pass independently re-derives asleep truthiness and would otherwise have silently bypassed the other two. Also fixed in the same pass: asleep-class room-timer default was 30 minutes, now a real 8 hours, closing a genuine format bug (`'00:%02d:00'` hardcoded 0 hours and silently broke for any duration ≥ 60 minutes — which 480 obviously is).

- **`autosleep_schedule` — for rooms where "night" isn't at night.** A community request: shift workers, or anyone whose sleep schedule doesn't track the house's clock. Tag any truthy-resolving entity (a toggle, a calendar, an HA `schedule.*` helper) with `autosleep_schedule` plus the room's own label, and it becomes **authoritative** for that room — fully replacing the night→wake window check rather than widening it. `asleep_window_disable` still outranks it if a room somehow carries both labels. Same label-existence idiom every other opt-in construct here already uses, no new mechanism.

- **`asleep_hold` — a third, independent path into Asleep.** Structurally identical to `entertaining_hold`/`guest_hold`, but feeds the `asleep` tier directly instead of `hold`. Tag a truthy-resolving entity with `asleep_hold` plus the room's label and the room reads `asleep` outright — no bed sensor, no trigger signal, no window check needed. Zero clock, zero decay: clears the instant the tagged entity goes false, or a manual override.

**Cascade order, current:**
```
emergency > manual override (room_control_manager) > asleep > engaged >
child-engaged > hold (wasp / entertaining / guest) > occupied (or fridge-door hold) > vacant
```

**Verified live** across the full incident-and-fix cycle: a real garage door/motion sequence produced the documented `vacant → occupied → hold` sequence correctly; `entertaining_hold`/`guest_hold` confirmed via tagged rooms with `last_trigger` correctly attributing each hold to its source boolean. The asleep-window gate hasn't been exercised against a full overnight cycle yet — built and reloaded same-day, no night had passed at verification time.

**Setup note:** six labels (`entertaining_hold`, `guest_hold`, `autosleep_disable`, `asleep_window_disable`, `autosleep_schedule`, `asleep_hold`) live in HA's label registry, not in git — the feature is a safe no-op until you create them: `zen_dojotools_labels mode=create label_list=["entertaining_hold","guest_hold","autosleep_disable","asleep_window_disable","autosleep_schedule","asleep_hold"] confirm=true`.

- **`domain_routing` gains a `crm` entry.** Twenty CRM's vendor/contact tooling was fully built and live but had no entry in Room Manager's own domain-routing table, making it undiscoverable through the path most callers actually use to find the right tool for a room.
- **Zone-mode disambiguation.** `zone_set`/`zone_remove`/`zones` renamed to `room_zone_set`/`room_zone_remove`/`room_zones` — the name collided with `zen_dojotools_zones`, the real HA `zone.*` geofencing tool, though the two share no other overlap (RM's zones are sub-room spatial pockets like "reading nook"). Zero external callers found, zero-blast-radius rename.

## Room Manager v3 — Wasp Gate, Coverage Tooling, and REFLEX Correctness

- **Wasp/hold rewritten again, this time to pure physical-space semantics.** No timer, no self-latch — true iff a `wasp_door` exists, the room opted into a new `wasp_enabled` gate, no `wasp_door` is currently open, and occupied/motion is live. The gate exists because rooms with an open archway instead of a real door (no way to tell "someone's inside with it shut" from "there is no door") would otherwise misfire constantly.
- **~14 new purpose-trigger platform entries** (HA 2024.9+) scoped by label instead of static entity enumeration — an additional live-signal source layered on top of the existing explicit `trigger_entities` list, not a replacement for it.
- **New diagnostic modes**: `trigger_audit` (which classes are purpose-trigger-covered vs. still need static wiring), `coverage_map` (unified diagnostic combining label-discovery gaps, trigger coverage, dormant-feature detection, and wasp-gate status — advisory only, never auto-applies), `wasp_enable` (read/write the room-level gate).
- **`room_occupancy` cabinet mirror** — every real room-state transition now also writes that room's full attribute set to the household cabinet, a read-surface companion to the native per-room sensors (which stay authoritative). Caught and fixed a real concurrency bug in the same pass: two rooms transitioning simultaneously raced on a shared dict drawer and clobbered each other; fixed with FileCabinet's nested-key support so each room gets an independent key.
- **REFLEX dry-run was gated backwards.** REFLEX on used to always fire for real even with dry-run also on — the one case dry-run is most useful for. REFLEX off with dry-run on used to still produce dry-run logs for a system that would never fire anything. Fixed across all 3 fire sites (the main scene resolver plus both nightlight paths, the latter two of which had no dry-run check at all): REFLEX off means nothing happens, period; REFLEX on + dry-run on simulates only, zero real side effects; REFLEX on + dry-run off fires for real.
- **Retired `checking` state fully purged** from every remaining live reference (label registries, diagnostic state lists, help text) — it had already been dropped from the core cascade but was still lingering as a "valid" entry in half a dozen other places.
- **Tool self-description stabilization**: `mode=help` was missing ~10 real modes entirely; REFLEX's explanation lived in one unstructured prose blob while every other mode got a clean one-liner; `reflex_assignments` converted from pipe-delimited strings to structured JSON, matching every other multi-field write in the tool. A follow-up UAT pass caught a third, independent bug — `tool_manifest` carries its own separate mode-description dict from `help`'s, already drifted, missing `reflex_dry_run` entirely.

## Manifest Audit & Shared Scanning

Manifest gains audit/inference fields and missing-label detection, closing the gap between what a household's tools claim to expose and what's actually wired up. Later in the release, the scanning itself got consolidated.

- **A shared collector, `zen_admintools_toolscan`, replaces five hand-rolled fan-out loops.** `toolmap` (below), `domains`, `label_audit`, `cert_audit`, and `audit` each used to scan `states.script` and call every tool's own `tool_manifest` independently — five near-identical loops that could silently drift from each other. All five are now thin callers of one collector, aggregating its results instead of re-scanning. Migrated one mode at a time: capture a live baseline, migrate, diff the new output against the baseline, mirror to the second box, repeat.
- **Deliberately not migrated**, and documented as such rather than left as an unexplained gap: `bootstrap_stacks` (its mutation call is interleaved with discovery in the same loop step — splitting would scan every tool twice), `bootstrap_kfc` and `repair`'s KFC half (a different discovery mechanism and collect verb the shared collector doesn't fetch), `health_refresh` (a deliberate staggered multi-wave sweep for load management, with its own admintools exclusion), `mcp_sync` (doesn't fan out over `tool_manifest` at all).
- **`dependencies=[]`** joins `inference{}` as a field every tool always reports on `tool_manifest()`, defaulting to empty — zero-effort compliance for tools that haven't declared any yet.
- **New `mode=toolmap`** on the manifest tool builds a declared (not observed) dependency graph from that field — per-tool rollup (`green`/`degraded`/`self_contained`) plus `nodes[]`/`edges[]`. A five-tool proof set using real edges from this release's own work (`persona_editor` → `certadmin` → `{manifest, identity, filecabinet}`, `room_manager` → `lights`) shows the shape works; most of the tool roster still reports `self_contained` simply because it hasn't declared dependencies yet. Deliberately scoped to what's statically declarable — a runtime call-tracing version would go stale immediately and wasn't attempted.
- **A compliance blind spot found and closed.** The admintools tier had been silently excluded from every audit-mode scan target since 2026-07-29 — a crash workaround for an unguarded `limit` variable that should have fixed the crash instead of routing around it. Root-caused and fixed across the three admintools tools that needed it; every audit mode now scans the full tool roster for the first time.
- **`mount_status` was reporting every cabinet as unmounted, always.** Two stacked bugs: a wrong-depth cabinet read (unwrapping one layer short of the actual value) and a loop that re-read the same outer target on every iteration instead of the entity actually being inspected. Both pre-flagged by their own stale TODOs, both fixed.
- **A real ticket-reference sweep**, prompted by a caught PII pattern: internal ticket numbers and reporter attributions had been leaking into code comments and field descriptions across a dozen-plus files, going back weeks. All removed — comment/description text only, no functional changes — and the practice is retired going forward.

## Hospitality Lifecycle — Arrival, Stay & Departure

Twenty CRM's stay-tracking already covered intake and turnover; this release fills in the middle — the household getting a heads-up before a guest actually arrives or leaves, not just recording the fact once it's happened.

- **`stay_prep_check`** — the arrival counterpart to the existing `stay_release` turnover flow. Scans upcoming reservations within a configurable lookahead window (default 3 hours) and, once per stay, spawns a Taskmaster prep task carrying the guest's stored preferences (allergens, music, spa) plus a Postman notice. Deliberately a human-in-the-loop chore rather than direct room actuation — there's no entity-level room-to-device resolution built yet, and getting that wrong on an allergy-relevant prep is worse than asking a person to check.
- **`checkout_status`** — a read-only, zero-side-effect query listing active stays with checkout inside a wide browsing window (default 24 hours), callable anytime.
- **`stay_checkout_check`** — the departure counterpart, firing once per stay inside a tighter window (default 3 hours) with the same task-plus-notice shape. Doesn't replace `stay_release`, which still owns the actual turnover dispatch once checkout happens — this only nudges that it's approaching.
- **Notification times read naturally.** Both nudges originally surfaced the raw stored UTC timestamp; both now show a humanized local time (`Wed Aug 19, 06:53 PM`) in the task note and the push, while the underlying JSON response keeps the machine-readable value unchanged.
- **A real storage bug, found building this.** Stay/reservation/appointment creation stored a local wall-clock time with a literal UTC marker and no conversion — typing the check-in time from the tool's own documentation examples landed five hours off. Fixed at the shared normalization point, which surfaced a second bug: several status-computation call sites assumed a naive timestamp meant local time, silently re-breaking status the first fix was meant to unbreak. Both fixed together; a stay's ACTIVE/RESERVED status now agrees with its actual stored time everywhere it's computed.
- Guest identity and permission delegation — an owner granting a guest their own scoped access rather than relying on one household-wide guest flag — is explicitly out of scope this release. Held for the next one.

## Good Fences — Boundaries Without the Attitude

A good host knows which doors don't open themselves — the identity-gate work covered above is most of this release's security story. Two smaller pieces round it out.

- **`zen_dojotools_urgency_handler` — a real implementation, not a stub.** The dispatcher had a registered no-op sitting where a genuine third urgency path lands: a KFC component flagging `action_required=true` at low urgency — needs a human, nothing to automate — with no automatic remediation and no push-worthy signal. Traced against the emission site to confirm it was live-wired and silently dropping real events, not dead code. Now routes to a real Taskmaster task, scaled by urgency, closing the gap.
- **Postman's `agent_auth` eligibility check flipped fail-closed.** A stub `true` sat under a `TODO` for the real check, with zero live callers today — but it would have silently authorized the first caller that showed up. The dangerous default is fixed; the actual eligibility policy (who's allowed to approve what) is still a deliberate design decision, not yet made.

## Query, Recorder & Prompt Correctness

- **ZQ-1 filter validation** — `filter_json` keys that don't exist (a stray `domains` instead of `domain`) used to vanish silently, producing a confidently-empty result indistinguishable from a real zero-hit query. Both `dry_run` and live responses now carry a `warning` field naming the bad key.
- **State-class-aware history stats** — requesting `mean`/`min`/`max` against a `total`/`total_increasing` energy sensor (SPAN, Emporia Vue) used to silently return empty buckets; the recorder call now branches on `state_class`. New `period_total_24h` gives a direct answer for "how much did this use today," cross-checked against recorder's own `sum` statistic and flagged when the two disagree by more than 2x — a real divergence caused by `statistic_id` re-registration on entity relabel, not a usage spike.
- **`sensor.home_overview` gains a real `rooms` attribute.** Friday's live prompt template had expected this attribute since the mechanism was built; it never existed, so the room-state section of every prompt had silently rendered empty. Fixed lean, per-room, one flat `{room: state}` dict — discovered via `occupied_active`, unconditionally present on every v3 room-state sensor.

## Identity Gates — Locks, Covers, Security, Room Manager, ZenLux, Climate, Spa, and a Real Self-Escalation Hole Closed

A new pattern lands this release: certain actuations are risky enough that "the agent is allowed to call this tool" isn't sufficient on its own. Four tools — `zen_dojotools_locks` (new), `zen_dojotools_covers`, `zen_dojotools_security_manager`, and `zen_dojotools_infra`'s container-control codex — now gate their riskiest actions behind a certification the household grants explicitly, with the highest-risk actions additionally requiring a fresh live yes/no every single time, no standing exception.

- **`zen_dojotools_locks` — new.** Room-targetable lock/unlock for the `lock.*` domain, the gap `zen_dojotools_covers` already had closed for `cover.*`. Full Keymaster code-slot detail on inspect — PINs are never surfaced, only whether a slot is set. Real parent/child Keymaster sync topology, found after three wrong turns (Z-Wave's bulk config-parameter service doesn't work for this; Keymaster's own entities aren't area-assigned or registered under a discoverable integration domain the obvious way).
- **A self-escalation hole, found and closed.** The tool that *grants* a certification had zero gating of its own — any caller could certify itself for anything, including the very capability an identity gate was built the same session to protect. Closed with a live cert catalog (calculated fresh from every tool's own self-declaration, not a hand-maintained file that can silently drift out of sync) plus a mandatory fresh live household-admin acknowledgment on every grant or revoke.
- **`zen_dojotools_covers` gets the same treatment.** New asymmetric-risk cert: closing any cover is cert-only, opening a barrier-class cover (garage door, exterior door, gate) requires the cert *and* a fresh live ack every call, opening an ordinary window covering stays cert-only. A real pre-existing bug surfaced building the gate logic: `position=0` (a legitimate "close" call) was being silently coerced to "no position given" by a Jinja idiom that treats any falsy value as unset, not just a genuinely missing one.
- **`zen_dojotools_security_manager` gets the same treatment.** Arming and alert-policy changes require the cert; disarming — the highest-risk direction — additionally requires the fresh live ack every time, no standing shortcut.
- **A scoped admin override**, added deliberately after the zero-trust default proved right in principle but heavy-handed in practice: a household admin can exempt specific targets (a specific door, a specific container) from the every-call live-ack requirement, without weakening the cert requirement itself or reopening the self-escalation gap. Granting the exemption still requires the same live ack as any other certification change.
- **A shared "get a live yes/no" chokepoint**, extracted after the same fire-and-poll pattern turned up hand-rolled independently in four different places. The extraction itself surfaced two more real bugs: the default notification path had never actually been capable of capturing a response since it was first written, and the dispatch-success check was testing for a response key that the underlying dispatch call never actually returns — both fixed at the single shared point rather than in each of the four call sites separately.
- **A canonical response-shape pilot** (`envelope()`) separating "did the call itself succeed" from "what did the tool actually find" — two real tools converted as the first adopters. Building it surfaced its own real bug: one malformed entry in an unrelated internal queue could have silently broken every tool response using the new shape, not just the one call that touched the bad entry; fixed before it shipped anywhere.
- **Room Manager v3 gains BLE-informed occupancy** (informational only this phase — doesn't yet feed any state decision) and a purpose-neutral vibration signal class with an anomaly-gated "the load is done" detector for laundry-style use cases, filtering out a brief bump from being mistaken for a finished cycle.
- **A real, already-shipped guidance gap corrected**: agent-assisted new-room deployment previously suggested an agent with file-write access could write configuration directly into a live package file as an exception case. That's wrong regardless of what access a given session happens to have — corrected to route through a proper copy-paste deployment template instead.
- **Scope resolution centralized to one place.** Every cert-gated tool was independently re-implementing "is this target covered by an admin's scope exemption" — five copies of the same logic that wouldn't have survived the deny-list ACL format landing later without five separate rewrites. Replaced with a shared macro; every gated tool now asks identity instead of computing it locally. Surfaced an unrelated bug along the way: an invalid input-selector config mode had taken an entire core tool offline with no error surfaced anywhere, found only by bisecting against a known-good copy.
- **Room Manager gains its own identity gate.** Moving a room out of a human-set Paused state now requires a certification and, like the highest-risk actions elsewhere, a fresh live acknowledgment every time unless the specific room is covered by a granted scope exemption — the "only a human can un-pause it" rule this release already documented is now actually enforced, not just intended.
- **ZenLux gets real switch control and a full rewrite.** `light.*`-only control was a real, if unnoticed, gap — every write action called light-domain services exclusively even where a switch was the logical target. Now supports `switch.*` directly (domain-agnostic toggle, explicit switch set, full room/role resolution), gained its own identity gate, absorbed the scene-staging workaround for a real HA persistence limitation (relocated in from Room Manager, on the principle that a write belongs with the tool that owns the domain it's acting on), and converted to the same single-entry/single-exit response shape as the rest of this release's gated tools. Two generic risks surfaced doing that conversion by hand, worth knowing for anyone doing the same kind of rewrite: a validation guard's early result can be silently overwritten if the code that follows it isn't explicitly told to skip when a result already exists, and a config-check pass does not catch a control block sitting at the wrong YAML indentation level — syntactically valid, semantically dead, only caught by comparing against a known-good conversion or by actually testing it live.
- **A real deny primitive, not just allow-scoping.** `cert_scope` entries can now explicitly deny a specific target, hard-blocked ahead of the certification check with no live ack ever offered — distinct from an unscoped target, which still asks normally. A second grant for an already-held certification now merges into the existing scope instead of silently replacing it (a real data-loss risk in the earlier version: adding one new exemption used to wipe every prior one unless the caller re-sent all of them), with a dedicated per-entry removal path that doesn't require re-granting the whole certification.
- **The climate tool gets real auth and inherits `fan.*`.** Zero gating before this release — any caller could actuate a thermostat freely. New cert-only gate, no live-ack tier (nothing here is exterior-security-grade). Also closes a real, previously-unnoticed gap: there was no general-purpose fan control primitive anywhere in the codebase, only a hot-tub tool's hardcoded internal fan calls. The climate tool now owns `fan.*` directly — speed, preset, oscillation, direction — with the same fail-closed-on-unsupported-feature discipline it already applied to thermostats.
- **A full audit for identity-gate end-runs found two real gaps and closed both.** ZenZork's text-adventure commands (`open`/`close`/`use`/`push`/`pull`) were issuing raw lock/cover service calls directly against real household hardware, completely bypassing the certification and live-ack requirements those domains now enforce everywhere else — a game command could open a real garage door with zero identity check. Rerouted through the same gated tools, and — since a game session has no legitimate path to a real live acknowledgment — every such action now runs in preview mode by default, narrating from the real authorization check without ever performing the real actuation. The spa/hot-tub tool had the identical shape of gap on jets, lights, water temperature, and its cover, closed the same way as everywhere else in this release.
- **Room Manager's own write surface joins the gated tools**, two certifications covering roughly 35 modes: structural topology edits, and behavioral/state-machine writes. Both read-open, cert-only, deny-hard-blockable. The one asymmetry preserved deliberately: setting a room to Paused (increasing caution) never needs permission; only taking it back out of Paused does.
- **`scene_handling` — declared but never actually enforced, now gated for real.** `mode=scene_stage` snapshots and restores a whole room's light/cover/climate/media/switch/fan/humidifier state, but had never been added to the write-mode list that triggers the room-lock guard or any cert check — the certification existed on paper only. Gated at the action level, same shape as the other room-wide write certs: a caller needs `scene_handling` regardless of which domains' own certs it separately holds.
- **CertAdmin — a new admin-only cert authority.** `cert_grant`/`cert_revoke`/`cert_list` moved out of the agent-facing persona editor into a new admintools-only tool, never reachable by an agent even via MCP. Enables a genuinely new capability on top: an admin can waive the live-ack requirement for a specific cert (e.g. "don't ask every time I open the garage"), gated behind three independent layers — live-ack, `confirm_action`, and an exact-phrase acknowledgment — without softening live-ack for anyone else. The persona editor's own schema has nowhere to declare the waiver fields, so there's structurally nothing for an agent to pass even if it tried.
- **A compliance blind spot found and closed.** Manifest's audit/`cert_audit` scan-target builders had silently excluded the entire admintools tier since 2026-07-29, a crash workaround that should have fixed the crash instead. Root-caused and fixed across three admintools tools; every audit mode now scans the full tool roster, admintools included, for the first time. `cert_audit` also gained `my_certs`, cross-referencing its live catalog against a target's actual holdings in the same call.
- **A script-entity naming trap, caught by a live ticket.** An approved cert grant hard-failed with `ServiceNotFound` on a `script:`-platform tool whose `entity_id` had drifted from its `unique_id` after an old alias cleanup — a class of drift `automation:` entities structurally can't have, and one no reliable Jinja-side guard exists for in this HA version. Fixed by the household admin renaming the entity by hand; mitigated going forward with a new static `mode=troubleshooting` on the help tool (fast diagnosis, not prevention) plus defense-in-depth fault isolation at the persona-editor→certadmin boundary.
